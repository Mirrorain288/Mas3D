# Spec Delta

## Purpose

定义游戏与 AstrBot 之间的会话桥接：游戏中的 Monika 与 QQ 上的 Monika 是同一个会话身份、同一份记忆，同时规定往返协议、来源标记、失败降级与安全边界。

## ADDED Requirements

### Requirement: 游戏会话绑定到既有的 AstrBot 会话身份

系统 SHALL 通过配置指定游戏所使用的 AstrBot 会话标识（unified_msg_origin），默认指向 QQ 私聊会话；游戏内产生的消息 MUST 进入该会话的同一份对话历史，从而与 QQ 侧共享上下文与人设。

#### Scenario: 共享记忆
- **WHEN** 玩家在游戏中告诉 Monika 一件事，随后在 QQ 上询问
- **THEN** QQ 侧的回复体现出她记得游戏里发生的事，且两边的对话历史指向同一个会话记录

#### Scenario: 会话标识可配置
- **WHEN** 部署者把游戏会话改为另一个不存在的会话标识
- **THEN** 游戏按该标识新建会话并正常工作，不因找不到历史而失败

### Requirement: 桥接以请求-响应方式承载一次对话回合

系统 SHALL 定义一次对话回合的请求与响应：请求包含玩家文本与会话标识；响应 MUST 包含可展示的回复文本，并 MAY 包含结构化的表现指令（情绪、注视、动作意图）。响应 MUST 在预设的时间预算内完成或明确失败。

#### Scenario: 正常回合
- **WHEN** 前端提交一条文本
- **THEN** 前端在时间预算内收到回复文本与可选结构化指令，并据此更新界面与角色表现

#### Scenario: 结构化指令缺失
- **WHEN** 后端只返回纯文本
- **THEN** 前端仍正常展示回复，表现层按文本推导或保持待机，不视为错误

### Requirement: 游戏消息带有可识别的来源标记

系统 MUST 让进入 AstrBot 会话的游戏消息带有可识别的来源标记，使对话历史能区分"出现在 3D 教室中"与"出现在 QQ 聊天中"，且 MUST NOT 让该标记破坏 QQ 侧的可读性。

#### Scenario: 标记存在
- **WHEN** 检查共享会话的历史记录
- **THEN** 游戏产生的消息可被识别为来自游戏，而不是与 QQ 消息完全无法区分

#### Scenario: QQ 侧可读
- **WHEN** 在 QQ 客户端查看这段历史
- **THEN** 游戏消息仍然可读，不出现原始协议字段或控制字符

### Requirement: 桥接必须对失败降级而不是让游戏不可用

系统 MUST 在后端不可达、请求超时、模型调用失败、返回内容不可解析时，让游戏继续可用：界面展示明确状态，并由本地兜底产生一条可读回复或保持沉默，玩家可以继续输入。

#### Scenario: 后端超时
- **WHEN** 后端在时间预算内没有响应
- **THEN** 前端结束等待、提示超时、可用本地兜底回复，并允许重试

#### Scenario: 模型侧错误
- **WHEN** 后端返回错误（模型不可用、额度耗尽、内容被拒）
- **THEN** 前端展示对应的可理解提示，游戏其余功能不受影响

#### Scenario: 后端崩溃不影响既有功能
- **WHEN** 桥接进程异常退出
- **THEN** 已有的 QQ 机器人功能与其会话数据不被破坏

### Requirement: 浏览器不得持有任何模型服务凭据

系统 MUST 保证所有外部模型与后端的访问凭据只存在于服务端；浏览器侧代码与运行时配置 MUST NOT 包含可被玩家读取的 API 密钥。

#### Scenario: 检查前端产物
- **WHEN** 检查构建后的前端资源与运行期配置
- **THEN** 不存在任何 provider 密钥或后端管理凭据

### Requirement: 同一会话的回合串行处理并受速率保护

系统 SHALL 对同一会话的对话回合串行处理，并 SHALL 对异常高频的请求施加限流；限流触发时 MUST 以可理解的提示告知玩家而不是静默丢弃。

#### Scenario: 连续快速发送
- **WHEN** 玩家在极短时间内发起多次请求
- **THEN** 请求按顺序处理或被限流，历史记录不出现乱序或交错

#### Scenario: 限流反馈
- **WHEN** 请求因限流被拒
- **THEN** 界面提示"发送过于频繁"，并允许稍后重试
